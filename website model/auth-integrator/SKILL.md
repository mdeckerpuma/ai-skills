# Auth Integrator

Adds complete Supabase authentication to an app generated by the website-model pipeline.
Writes three auth pages (login, signup, password-reset) with full UX (loading states,
inline errors, redirects). Rewrites auth-guard.js with real role-based logic derived from
blueprint.json. Outputs Supabase RLS SQL snippets the user applies to their database. Never
hardcodes credentials. Never silently skips the RLS output.

---

## Guardrails

- **Never hardcode auth credentials or JWT secrets.** All `SUPABASE_URL` and
  `SUPABASE_ANON_KEY` references in generated pages must come from `window.__env` or the
  shared `supabase-client.js` — never written directly into page `<script>` blocks.
- **Never remove existing page content when updating auth-guard.js.** Only replace the
  auth-guard logic block — preserve any custom HTML, styles, or other script content the
  user may have added. Show a diff before any overwrite.
- **Never silently omit the RLS SQL output.** If RBAC is configured (blueprint has non-empty
  `components[].roles`), always output the full set of RLS policy SQL statements. Do not
  skip or summarize them — the user must see the exact SQL to apply it to Supabase.
- **Never proceed if blueprint.json is missing.** auth-integrator derives roles and
  protected routes from blueprint.json. Without it, it cannot generate correct RBAC.
  Hard stop:
  > "No blueprint.json found. Run /app-architect first."
- **Never apply auth-guard to public pages.** Only guard components where
  `blueprint.components[].roles` is non-empty AND `blueprint.routes[].auth === true`.
  The login, signup, and password-reset pages themselves must never be guarded.

## Gotchas

- **OAuth providers not enabled in Supabase dashboard.** The most common real-world failure:
  Google/GitHub login buttons are generated correctly but the provider isn't activated in
  the Supabase project's Auth settings. The button will trigger a redirect that immediately
  fails. Always output a post-generation checklist:
  > "IMPORTANT: OAuth buttons will fail until you enable each provider in your Supabase
  > project → Authentication → Providers. See the checklist below."
  Include step-by-step for each enabled provider.

- **Auth-guard applied to signup/login pages.** A logic error that locks users out of the
  app entirely. The auth flow pages (login.html, signup.html, reset-password.html) must
  explicitly never import auth-guard.js. Double-check this before writing each file.

- **RLS SQL generated but never applied.** auth-integrator outputs SQL snippets but cannot
  run them — the user must apply them in the Supabase SQL editor. Without RLS, protected
  data is accessible directly via the Supabase API even if the frontend guard is correct.
  Always remind the user after outputting SQL:
  > "The frontend role guard is active. The RLS policies above are NOT yet applied to your
  > database — paste them into Supabase SQL editor to enforce protection at the API level."

- **Redirect after login sends user to wrong page.** By default, login success redirects to
  `/index.html`. If the user was deep-linking to a protected page, they lose their target.
  The generated login page should check for a `?redirect=` query param and use it if
  present, otherwise fall back to `/index.html`.

- **blueprint.components[].roles is empty.** If roles are not defined, RBAC cannot be
  generated. Rather than generating broken guards, stop:
  > "blueprint.json has no roles defined on any component. Generate basic auth (logged in /
  > not logged in) without role differentiation? (yes/no)"
  If yes, generate simple session-based guards only.

## Steps

### 0 — Pre-flight

1. Identify the project. Accept explicit project name argument, or default to the most
   recently modified project folder under `website model\projects\`.

2. Read `blueprint.json`. Validate presence of:
   - `app.name`
   - `stack.auth` (must be `supabase` — if `none`, stop: "Blueprint specifies no auth. Nothing to do.")
   - `components[]` with `roles` arrays
   - `routes[]` with `auth` flags

3. Check for existing auth files in `projects\[app-name]\pages\`:
   - `login.html`, `signup.html`, `reset-password.html`
   - If any exist, show a diff summary and ask: **Overwrite / Skip / Cancel** per file.

4. Check `js\auth-guard.js` — if it exists, show current content and ask: **Replace / Keep / Cancel**.

5. Load memory: `preferred_auth_provider` (to set default active provider).

---

### 1 — Resolve auth configuration

From `blueprint.json` and memory, determine:

| Config | Source | Value |
|--------|--------|-------|
| Auth provider | `stack.auth` | supabase |
| Protected routes | `routes[].auth === true` | list of paths |
| Role definitions | `components[].roles` | array per component |
| Active auth methods | `preferred_auth_provider` memory | email-password / magic-link / oauth |

If `blueprint.components[].roles` is empty across all components — flag it (see Gotchas)
and ask before continuing.

---

### 2 — Generate auth pages

Write three pages to `projects\[app-name]\pages\`:

#### login.html

Full auth flow:
- Email + password form (always included)
- Magic link button (if `preferred_auth_provider` includes magic-link)
- Google / GitHub OAuth buttons (if `preferred_auth_provider` includes oauth)
- Submit button disables + shows spinner during Supabase call
- Inline error display for: wrong credentials, email not found, rate limited
- On success: check `?redirect=` query param → redirect there or to `/index.html`
- Link to signup.html and reset-password.html
- **Never import auth-guard.js**

```javascript
// Core login logic pattern
const { error } = await supabase.auth.signInWithPassword({ email, password });
if (error) { showError(error.message); } else { window.location.href = redirect || '/index.html'; }
```

#### signup.html

- Email + password fields + confirm password client-side validation
- Supabase call: `supabase.auth.signUp({ email, password })`
- On success: show "Check your email to confirm your account" message
- Error handling: email already in use, weak password
- Link to login.html
- **Never import auth-guard.js**

#### reset-password.html

Two states driven by URL:
1. **Request state** (no `?token` in URL): Email input → calls `supabase.auth.resetPasswordForEmail(email)`
   → shows "Check your email" message
2. **Reset state** (`?token` present): New password + confirm → calls `supabase.auth.updateUser({ password })`
   → on success redirect to login.html
- **Never import auth-guard.js**

### 3 — Rewrite auth-guard.js

Replace `js\auth-guard.js` with role-aware implementation:

```javascript
import supabase from './supabase-client.js';

const { data: { session } } = await supabase.auth.getSession();
if (!session) {
  const redirect = encodeURIComponent(window.location.pathname + window.location.search);
  window.location.href = `/pages/login.html?redirect=${redirect}`;
}

// Role check — CURRENT_PAGE_ROLES injected per-page at generation time
const ALLOWED_ROLES = [/* roles from blueprint for this component */];
if (ALLOWED_ROLES.length > 0) {
  const userRole = session.user.user_metadata?.role;
  if (!ALLOWED_ROLES.includes(userRole)) {
    window.location.href = '/pages/unauthorized.html';
  }
}
```

Each protected page's import of `auth-guard.js` must be updated to pass its allowed roles.
Revisit each protected HTML file in `pages\` and update the auth-guard import or inline the
role check for that page's role list.

Also write `pages\unauthorized.html` — a simple "Access Denied" page with a link back to
`/index.html`.

---

### 4 — Update routes.js

Add the three new auth routes to `js\routes.js`:

```javascript
'#/login':          'pages/login.html',
'#/signup':         'pages/signup.html',
'#/reset-password': 'pages/reset-password.html',
'#/unauthorized':   'pages/unauthorized.html',
```

---

### 5 — Generate RLS SQL

For each table in `blueprint.schema[]` where the corresponding component has non-empty
`roles`, output a SQL block:

```sql
-- RLS for [table] — apply in Supabase SQL editor
ALTER TABLE [table] ENABLE ROW LEVEL SECURITY;

-- Allow [role] to read all rows
CREATE POLICY "[table]_select_[role]" ON [table]
  FOR SELECT USING (
    auth.jwt() ->> 'role' = '[role]'
  );

-- Allow [role] to insert
CREATE POLICY "[table]_insert_[role]" ON [table]
  FOR INSERT WITH CHECK (
    auth.jwt() ->> 'role' = '[role]'
  );

-- Allow [role] to update their own rows (or all rows for admin)
CREATE POLICY "[table]_update_[role]" ON [table]
  FOR UPDATE USING (
    auth.jwt() ->> 'role' = '[role]'
  );

-- Allow [role] to delete
CREATE POLICY "[table]_delete_[role]" ON [table]
  FOR DELETE USING (
    auth.jwt() ->> 'role' = '[role]'
  );
```

Generate one block per table × role combination. Output all SQL in a fenced code block
the user can copy directly into Supabase SQL editor.

Also write the SQL to `projects\[app-name]\rls-policies.sql` for safekeeping.

## Versioning & Iteration

- If a project needs custom login UI (branded, multi-tenant) → add a style-override step
  that reads `css\styles.css` variables and applies them to auth pages.
- If role assignment at signup is needed → add a Step 2b that generates a Supabase
  database trigger to auto-assign role from a `default_role` config.
- If magic link is frequently skipped → remove it from the default output and gate it
  behind explicit user confirmation.
- After 3+ real auth integrations → review whether the RLS SQL pattern works correctly
  with Supabase's `auth.jwt()` claims — Supabase may require `auth.uid()` patterns
  depending on how roles are stored (user_metadata vs. custom claims).
